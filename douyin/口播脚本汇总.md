## 01 · reactive 与 Proxy（约 55s）

【开头钩子 0-5s】
你知道吗？Vue2 里给数组第 0 项赋值，页面根本不会更新！

【正文 5-40s】
因为 Object.defineProperty 有三个先天缺陷：新增属性拦不住、索引赋值拦不住、删除属性拦不住，Vue2 只能用 $set 打补丁。
Vue3 直接换了武器：Proxy。
更狠的是，我读了源码发现一个细节：嵌套对象是「懒代理」——你读到哪个属性，Vue 才给哪个创建代理。所以初始化一个几百个字段的大对象，完全不卡。
还有，给同一个属性赋两次相同的值，第二次不会触发任何更新。你平时的「无谓更新」，很多在这一步就被挡掉了。

## 02 · effect 与依赖收集（约 60s）

【开头钩子】
为什么你改了一个无关的数据，Vue 页面不会乱动？这背后藏着一个精妙的清理机制。

【正文】
组件渲染、watch、computed，背后都是同一个东西：effect。
它的执行只有六步，最关键的两步：跑之前，先清掉上一轮记录的所有依赖；然后把自己挂到全局变量 activeSub 上——现在是我，在读数据。
为什么要清理？假设有个函数：条件为真读 a，为假读 b。条件切换之后，旧的 a 依赖就是死依赖，不清理的话，改 a 也会让页面白跑一次。Vue 每次重跑前都把它清掉。
Vue 3.5 还把依赖管理重构成了双向链表，摘除一条依赖只要 O(1)，性能直接提升 40%。

## 03 · ref 与 computed（约 50s）

【开头钩子】
为什么 ref 必须写 .value？少写一个就报错？

【正文】
因为原始值根本没有属性可以拦截！数字、字符串，你给它赋值就是纯粹的内存操作，谁也拦不住。
唯一的办法：把它包成对象，给 value 这个属性加 get 和 set——读写 .value 才有拦截点。所以 .value 不是语法糖，是响应式的命门。
computed 更妙：依赖变了，它不重算，只打一个「脏标记」；等真的有人来读，才执行计算；算完还要对比版本号，结果没变连下游都不惊动。
这就是 computed 又快又省的原因：惰性求值。

## 04 · watch 与 nextTick（约 55s）

【开头钩子】
同一秒把数据改三次，watch 回调执行几次？九成的人答错。

【正文】
答案是：一次。
所有秘密在 scheduler 调度器里：每次数据变化，任务不是立刻执行，而是丢进一个 Set 队列——Set 自动去重，三次修改只剩一个任务。
然后 Vue 用一个 Promise.then 把刷新排到微任务里。你的 nextTick 回调，就是排在这轮 DOM 刷新后面的另一个 then——所以 nextTick 里拿到的永远是最新 DOM。
还有一个细节：队列会按组件 id 排序，父组件永远先更新，子组件后更新，顺序永不乱。

## 05 · 编译器三步走（约 55s）

【开头钩子】
你每天写 template，但它最后变成了什么，你知道吗？

【正文】
答案：一段纯 JavaScript 函数。
Vue 编译器就三步：parse 把字符串切成抽象语法树；transform 遍历这棵树打优化标记；codegen 把树拼回代码字符串。
看这个编译产物：静态的节点被提到了函数外面——整个应用生命周期只创建一次；动态的节点后面跟了个数字 1，意思是「只有文字会变」。
编译器的哲学就一句话：编译时能做的判断，绝不留给运行时。
你写的每一行模板，都是被这样优化的。

## 06 · patchFlag 与 Block（约 60s）

【开头钩子】
1000 个节点只有 1 个变量在变，Vue3 凭什么秒更新？

【正文】
因为编译器提前埋了三件武器。
第一件：patchFlag，位标记。每个动态节点带着「我哪里会变」的编号，更新时按位判断，只处理标记的变化。
第二件：Block。每个动态节点会被收集进一个数组，diff 时只遍历这个名单——静态节点根本不在名单里！比较次数从 1000 降到个位数。
第三件：事件缓存。你的 @click 函数第一次创建后就缓住了，引用永远稳定，子组件不会因为父组件重渲染而无谓更新。
所以有个反直觉的结论：手写 render 函数反而比模板慢——因为绕过了编译器。

## 07 · 渲染器 patch（约 50s）

【开头钩子】
Vue3 最大的源码文件有 2700 行，但它的骨架，五句话就能讲完。

【正文】
核心函数叫 patch，一个分流器：
新旧是同一个节点？什么都不做。
类型或 key 不同？旧的整个卸载，新的整个挂载。
普通元素？有编译标记走快通道，没有就全量对比。
组件？用渲染函数包一层 effect，数据一变自动重渲染。
最巧的细节：更新时新节点直接接管旧节点的真实 DOM 引用，之后所有修改都作用在这一个节点上——绝不重建。
列表为什么必须加 key？因为 key 变了等于类型变了，整个组件从头再来。

## 08 · diff 与 LIS（约 60s）

【开头钩子】
列表从 a、b、c 变成 c、a、b，怎么用最少的移动完成更新？Vue3 用了一道算法题。

【正文】
这道题就是：最长递增子序列，LIS。
Vue3 的 diff 分五步：头部相同的直接复用；尾部相同的直接复用；剩下的乱序区，先建一张 key 到新位置的映射表；再遍历旧列表生成映射数组；最后求 LIS——
在新列表里相对顺序没变的节点，就是 LIS，它们原地不动；只有不在 LIS 里的节点才需要移动。
实测：abc 变 cab，只移动一个节点！
用的算法是耐心排序，二分加回溯，O(n log n)——就是刷题原题的变形。
这也回答了「为什么 key 不能用 index」：用 index，插入一个元素全列表都要动。

## 09 · 生命周期顺序（约 50s）

【开头钩子】
父子组件，mounted 谁先执行？updated 谁先执行？答案居然是相反的！

【正文】
mounted：子先父后。
因为父组件渲染时递归挂载子组件，子的钩子先入队；父的要等整棵子树挂完才轮到自己。谁先入队谁先执行。
updated：父先子后。
因为更新从父组件开始，它的任务 id 更小，先执行；patch 从上往下传播，才轮到子组件。
一个冷知识：onMounted 的本质，就是往实例上挂一个数组、把你的函数 push 进去——所以组合式 API 可以注册任意多个同名钩子，按注册顺序执行。
还有：setup 比 created 更早，它天生就是 beforeCreate 和 created 的替代品。

## 10 · KeepAlive（约 55s）

【开头钩子】
KeepAlive 为什么能让页面切换后状态不丢？源码朴素得让人感动。

【正文】
它的全部家当：一个 Map 存缓存的节点，一个 Set 记使用顺序。
命中缓存？直接复用旧的真实 DOM——组件状态就存在里面，天然保留。同时把这个 key 移到队尾，标记「最近使用」。
缓存满了？淘汰队首——最久没用的那个。一个 Map 加一个 Set，这就是完整的 LRU 算法，也是高频面试手写题。
所以缓存组件切换时，跑的不是 mounted 和 unmounted，而是 activated 和 deactivated。
Teleport 更绝：组件树的父子关系不变，但真实 DOM 直接挂到你指定的容器——两边解耦，所以它能逃出父级的 overflow 和层级限制。
