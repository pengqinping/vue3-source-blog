## 01 · reactive 与 Proxy

**标题**：Vue3 为什么抛弃 defineProperty？😭 3 个坑讲明白

**正文**：
写 Vue2 的都懂：新增属性不响应、数组索引赋值不响应、delete 不响应…全靠 $set 续命💊
Vue3 直接换武器 Proxy：拦截整个对象的操作，三个坑一次全解决✅
我读了源码才发现更狠的细节👇
1️⃣ 嵌套对象是「懒代理」：读到哪个属性才创建 Proxy，初始化大对象也不卡
2️⃣ 赋相同的值不会触发更新（hasChanged 拦截）
3️⃣ Map/Set 走的是另一套 collectionHandlers

## 02 · effect 与依赖收集

**标题**：读了Vue3源码，终于懂了什么是"响应式心脏"❤️

**正文**：
组件渲染、watch、computed…背后都是同一个东西：effect！
它的工作原理只有 6 步（附源码 run() 方法逐行拆解）：
1️⃣ 跑之前先 cleanup：清掉上一轮的旧依赖
2️⃣ 把自己挂到全局 activeSub：现在是我在收集依赖
3️⃣ 执行函数：所有响应式读取都被记账
4️⃣ 跑完恢复现场（支持嵌套）
最惊艳的是 3.5 的新架构：Dep/Link 双向链表，摘除一条依赖只要 O(1)⚡ 性能直接提升 40%
「为什么改一个无关属性不会乱更新」——答案就是 cleanup，我用 demo 复现了幽灵更新场景👀

## 03 · ref 与 computed

**标题**：.value 不是语法糖！是响应式的命门🔒

**正文**：
为什么 ref 必须写 .value？看了源码瞬间通透——
原始值（数字/字符串）根本没有属性可以拦截，只有包成对象、给 value 一个 get/set，读写才有「拦截点」🕵️
所以 .value 丢了 = 响应式丢了！
computed 更妙：依赖变化时只打一个「脏标记」DIRTY，没人读就不重算，读了才算，算完还会对比版本号决定要不要惊动下游🌊
这就是为什么 computed 又快又省（附 DEMO 运行实录：创建时不算/改了只标脏/读了才重算）

## 04 · watch 与 nextTick

**标题**：同一秒改3次数据，Vue只更新1次？nextTick真相🔍

**正文**：
面试题：同一 tick 里 count 改三次，watch 回调跑几次？DOM 更新几次？
答案：都只 1 次！原理就在 scheduler.ts：
1️⃣ 数据变化 → 任务进 Set 队列（自动去重，3次变1次）
2️⃣ Promise.resolve().then 统一微任务刷新
3️⃣ 按 uid 排序：父组件永远先于子组件更新
而 nextTick 本质就一行：Promise.then 排到本轮 DOM 刷新后面，所以回调里拿到的永远是最新 DOM✅
deep watch 的原理也超朴素：递归把对象读一遍强制收集依赖（大对象慎用！）

## 05 · 编译器三步走

**标题**：模板是怎么变成JS的？Vue编译器3步讲透🏭

**正文**：
你写的 <template> 最后变成了什么？答案是：一段纯 JS 函数！
编译器流水线只有三步：
① parse：字符串 → AST（用栈维护嵌套层级）
② transform：遍历 AST 打优化标记（patchFlag/静态提升）
③ codegen：AST → render 函数代码
我截了个编译产物图：静态节点被提到函数外面只创建一次，动态节点带着数字标记 1（TEXT）🚀
「编译时能做的绝不留给运行时」——这就是 Vue3 快的底层哲学
附我写的 100 行 mini 编译器，全链路可运行！

## 06 · patchFlag 与 Block

**标题**：Vue3比Vue2快在哪？3件武器说清楚⚔️

**正文**：
1000 个节点只有 1 个变量在变，Vue3 怎么做到秒更新？
编译器提前埋了三件武器：
1️⃣ patchFlag：位标记（TEXT=1/CLASS=2/STYLE=4…），更新时按位判断，只处理标记的变化
2️⃣ Block + dynamicChildren：动态节点打平收集进数组，diff 从「遍历整棵树」变成「遍历动态名单」，静态节点根本不进名单！
3️⃣ 事件缓存：handler 存进 _cache，引用永远稳定，子组件不会无谓更新
所以：手写 render 函数反而比模板慢——没有编译期标记只能全量 diff😏

**标签**：#Vue3 #性能优化 #前端 #源码学习 #面试

## 07 · 渲染器 patch

**标题**：2700行renderer.ts，核心其实只有一个patch🎯

**正文**：
Vue3 最大的源码文件 renderer.ts 有 2700 行，但骨架就一个函数：patch
分流逻辑5句话：
· 新旧是同一个 vnode → 什么都不做
· type 或 key 不同 → 卸载旧的，全新挂载
· 文本/注释/Fragment → 各自专属处理
· 普通元素 → mount 或 patchElement
· 组件 → setup + 渲染effect 包起来
还有个细节：更新时 n2.el = n1.el，复用真实 DOM 引用，绝不重建节点💰
列表为什么必须加 key？因为 key 变了 = 类型判定失败 = 整个重建！

## 08 · diff 与 LIS

**标题**：Vue3的diff竟然用了算法题里的LIS？！🤯

**正文**：
列表从 [a,b,c,d,e] 变成 [a,c,x,f,b]，怎么用最少的 DOM 移动完成更新？
Vue3 的答案：最长递增子序列（LIS）！
五步走：
① 头部相同的直接复用 ② 尾部相同的直接复用
③ 新列表建 key→index 映射 ④ 旧列表生成映射数组
⑤ 求 LIS：相对顺序没变的节点原地不动，只移动剩下的⚡
demo 实测：abc→cab 只移动 1 个节点！
LIS 用的是耐心排序，O(n log n)，二分+回溯，就是刷题时的原题变形📚
这也是「列表为什么要加唯一 key」的终极答案

## 09 · 生命周期顺序

**标题**：父子组件mounted谁先跑？源码给了标准答案👨‍👩‍👧

**正文**：
面试必考，源码一句话讲透：
mounted：子先父后✅
因为父组件 render 时递归挂载子组件，子的钩子先入队；父的要等整棵子树挂完才入队。谁先入队谁先执行！
updated：父先子后✅
更新从父组件开始（uid 小的 job 先跑），patch 自上而下传播。
还有个冷知识：onMounted 本质就是往实例上 push 一个包装函数到数组（instance.m = [fn]），所以组合式API能注册任意多个同名钩子，按注册顺序执行📝
setup 比 created 还早——它就是 beforeCreate/created 的替代品

## 10 · KeepAlive

**标题**：KeepAlive缓存怎么实现？就一个Map加一个Set🎯

**正文**：
读了 KeepAlive.ts 源码，实现朴素得感动：
· cache: Map 存 vnode
· keys: Set 维护「最近使用顺序」（Set 有序！）
命中缓存 → 直接复用旧 DOM，状态天然保留；keys.delete+add 把命中项移到队尾
超过 max → 淘汰 keys 队首（最久未使用）——这不就是手写 LRU 的算法题吗？！
所以缓存组件切换时跑的不是 mounted/unmounted，而是 activated/deactivated💡
include/exclude 白名单之外的组件连缓存门都进不了
另外 Teleport 的本质：虚拟树父子不变，真实 DOM 直接挂到指定容器，两者解耦，所以能逃离父级的 overflow/z-index 影响🚪
